# core/context — 上下文裝配

外掛的核心。在有限 token 預算內，把「文風指南 + 全文大綱 + 相關角色卡 + 本層產物 + 近章原文 + 會話歷史 + 使用者引用」按優先順序裝配成一次請求的訊息序列，並如實記錄裝了什麼、丟了什麼。

| 檔案 | 職責 |

| [tokenizer.ts](tokenizer.ts) | 門面：`estimateTokens`（= `countTokens`）與按預算擷取的 `takeHead` / `takeTail`。全倉庫幾十處呼叫點都走這裡。 |

## Token 計數是可替換的

改造前 `estimateTokens` 是一個寫死的函式，想換更準的演算法得改遍全倉庫。現在分三層：

1. **`TokenCounter` 介面**——`count(text)` 數 token、`charsFor(tokens)` 反推字元數（截斷要用），可選 `prepare()` 供需要載入 wasm/詞表的實現。
2. **登錄檔**——`registerTokenCounter()` 註冊、`useTokenCounter(id)` 切換。切換失敗（未註冊、`prepare()` 拋錯）時**保持原計數器並返回 false**，絕不讓「數不了 token」把寫作流程帶停。
3. **`HeuristicTokenCounter`**——預設實現，就是原來那套係數，零依賴、同步、永不失敗。它是所有降級路徑的終點。

要接 tiktoken 或服務商的 count_tokens 介面，寫一個實現註冊進去即可，`builder.ts` 一行都不用改。

**校準迴路**：服務商返回真實用量時（`usage` 事件 → `collect` 的 `onUsage` → `recordUsage`）記下「估算/實測」比值，`usageStats()` 可查。它**只用於日誌與展示，不自動修正估算值**——估算必須是純函式，否則同一份上下文兩次裝配會得出不同的預算判斷，「不靜默截斷」的明細也就不可復現了。沒給 usage 的服務商什麼都不記，不拿估算冒充實測。

## 分階段裝配

一次裝配由 `BuildRequest.action.stage` 決定帶什麼。四張配方在 [recipes.ts](recipes.ts) 裡，**順序即填充順序**：

| 階段 | 身份 | 帶什麼 | 明確不帶 |
|---|---|---|---|
| **架構** | 網文策劃編輯 | **架構三件（配置 / 前提 / 世界觀，P0 force）**、角色圖譜一覽（P0）、已有角色卡（P1）；排設定清單時另帶設定（P2：分類表與已有條目一覽，與規劃階段同一種帶法），排世界觀時帶命中與近幾章出現過的設定，其餘幾件不帶；**展開一條設定**（單條設定目標）另帶這一條（P0 force，含暗設）、已排細綱裡用到它的地方與定稿過的記錄（P1，合計封頂）、相關條目（P2）；**落定設定**（設定目錄上的 `settle`）歷史 P0、封頂 60%，設定提到歷史後面（P1）：討論裡提到的已有條目整條帶（含暗設），其餘一行 | 正文原文、大綱 |
| **大綱** | 策劃編輯 | **架構三件 + 角色圖譜一覽（只給近期活躍的一段，其餘只列名字）+ 故事結構指導 + 大綱（按遠近帶分三段：最近 10 章整條，P0 force；再往前一章一行、最多 100 章，不強制；更早的交給全文大綱）**、全文大綱與角色卡（P1）、設定（P2） | 正文原文、各章細綱（已經寫過的由全文大綱交代） |
| **細綱** | 劇情編劇 | 本章細綱（單章時，P0 force）、**架構三件 + 角色圖譜一覽（同大綱）+ 大綱裡這一次要拆的條目（這一批與前面還沒拆的空殼；已經拆過的不帶，之後的不帶，P0 force）**、前 3 章與後 1 章的細綱、前序細綱一覽（最近 30 章）、近幾章的連續性事實、敘事線（P1，按區間挑：沒收束的線與這幾章要收的伏筆，敘事線二期）、全文大綱（P1，接住一覽之前的）、結構指導；設定（P2：分類表、已有條目一覽，排新章時照抄已有的名字） | 正文原文 |
| **正文** | 作者 | **文風指南、全域要求、本章細綱（含「設定」一節）、上一章結尾（不許重演）、後 5 章細綱（邊界）、本章已寫末尾（接著寫時）、上一版（重寫時），都是 P0 force**；出場角色卡、架構三件（除全域要求）、前 3 章細綱（梗概 / 關鍵事件 / 狀態變更，單列「前幾章細綱」，沒定稿的標「計劃」）（P1）；全文大綱、設定（P2）；近 2 章正文（P3） | 情節大綱、更早各章的細綱（2026-10-21） |

**設定（`lore` 層，設定名錄）**：幾百條設定的書不能命中就整條塞，先排序、再分兩種形態裝、按詳細度封頂。順位：R0 本章細綱「設定」一節點名的、R1 關鍵詞命中（作者這次說的 → 本章細綱 → 本章已寫的末尾；**最長匹配**，2026-10-25：一個詞每一處都落在別人更長的名字裡——別的條目的標題與關鍵詞、名錄裡記著還沒建條目的、本章細綱「設定」一節點的——就不算，「潛入聖地秘境」不把上位概念「秘境」整條帶進來，`loreMentionsIn`）——**整條**（一句話 + 正文 + 尾巴：水位之後、本章之前定稿章裡關於它的新事實，條目落後於正文時模型照樣拿得到）；R2 前幾章定稿出現過的、R3 大綱 / 細綱階段其餘條目——**一句話**。R3 近 `rosterRecent` 章（這一次要排的第一章往前數，與規劃時的角色圖譜同一個數）出現過的在前，按這幾章裡出現的章數、再按最近出現的那一章；更早的在後，按全書出現章數（2026-10-25：從前一律按全書出現章數，寫到八十章開篇的高頻詞佔滿名額）；排設定清單與「完整」那一級只按全書出現章數。整條超了上限降成一句話、一句話超了上限丟，都寫原因；R3 超了只併成一條報（`lore:catalog`），不逐條刷明細。條目整合到本章或更晚時明細裡提醒可能含之後的事。續寫那幾輪也帶（只 R0、R1）。訊息裡整條的空行隔開，一句話的併成一張清單。

**展開一條設定（完善設定，2026-10-19，目標 `{ kind: 'lore', relPath }`，階段是架構）**：設定那張配方多掛兩層，目標不是單條設定時它們什麼都不帶（[layers/loreFocus.ts](layers/loreFocus.ts)）——`loreSelf`（P0 force）是焦點，這一條的一句話、關鍵詞與全部正文，暗設照規劃時的樣子標明（`loreBodyFor`），還只有一句話的在明細裡注一句；`loreMaterial`（P1）是兩樣原料（`views/loreMaterial.ts` 的 `expansionMaterial`）：**已排細綱裡用到它的地方**（沒定稿的細綱「設定」一節點名它的那一行、梗概與關鍵事件裡提到它的句子，帶章號）與**定稿過的記錄**（與建條目、整合同一份 `recordsAbout`），兩樣合計照整合的 `MATERIAL_TOKENS` 封頂——都放不下各佔一半、一邊用不完讓給另一邊，沒帶上的寫明帶到第幾章（第 2 條）。`lore` 層在這個目標上不提前返回：去掉目標條目本身，關鍵詞命中的來源在作者的話之外再加這一條的標題、關鍵詞、一句話、正文與上面那幾句（整條），同一個分類目錄裡的一行帶，給分類表（建議拆出的子條目要歸類），不給 R2、R3。訊息裡的順序是「定稿過的記錄 → 已排細綱裡用到它的地方 → 當前這一條設定」，緊挨著指令。焦點不按 `targetNo` 定位（`focus.no` 是 +∞），已寫正文的書也不按正文「整理」（`settingFromText` 跳過它）。系統提示的那一句與輸出合同在 [loreExpandPrompt.ts](loreExpandPrompt.ts)，不借 `LORE_ENTRY_SYSTEM`（那一份第 1 條是「不補完、不推測」）；放在 context/ 而不是 features/，因為本層不依賴 features/。

**設定條目的「暗設」（完善設定，2026-10-19）**：條目可選的第四節，讀者還不知道的真相（`model/loreFile.ts` 的 `splitLoreHidden` 認）。**正文階段（寫、接著寫、重寫、討論正文）與續寫**：整條只帶明面，這一條真有暗設被去掉的在明細 note 裡注一句「暗設沒帶：……」（第 2 條）；作者 @ 引用的設定條目（`attachments` 層，`lore` 種類）同樣去掉、同樣注一句。**規劃時（設定 / 大綱 / 細綱）**：整條帶全部，暗設挪到最後、標題統一換成「## 暗設（讀者還不知道）」（`LORE_HIDDEN_MARK`）。怎麼拆、怎麼標在 `layers/render.ts` 的 `loreBodyFor`，lore 層與 @ 引用共用。一句話（`loreBrief`）本來就跳過暗設。

**角色卡的「暗設」（敘事線重做，原「未收伏筆」）**：同一個口徑。`characters` 層在正文階段（寫、接著寫、重寫、討論正文，連同審稿、修稿——它們也是正文那一層）與續寫不帶這一節，這張卡真有暗設被去掉才注同一句；規劃時（架構 / 大綱 / 細綱）整張帶，暗設放在最後、標題同樣是「## 暗設（讀者還不知道）」（`render.ts` 的 `renderCharacter` / `cardHidden`，空的、寫著「無」的當沒有）。正文階段 @ 引用的角色卡同樣去掉。只帶要點時規劃帶身份 / 當前狀態 / 暗設，寫正文只帶身份 / 當前狀態（`essentialCardKeys`），明細照實寫。老卡裡的「未收伏筆」是認不出的小節，不讀。大綱、細綱合同裡「暗設」那條規矩的物件是「相關世界觀設定」「相關角色設定」兩處。

表裡與下文的章數、字數都是**上下文詳細度**預設那一級（「詳細」）的值，各級見下面[「上下文詳細度」](#上下文詳細度)一節。

四張都按 [總計劃](../../../docs/design/plans/2026-09-30-blueprint-pipeline-roadmap.md) §2.3 排：前三張二期，正文那一張三期（移植自 AI-Novel-Writer 的 `next_chapter_draft` 材料包），四期在它的 P2 加了 `evidence`。**執行卡與篇幅合同不是層**，由輸出契約拼在訊息最末（上游 GD:657 的順序）。

**正文續寫那幾輪**（`step.kind === 'continuation'`，generation/continuation.ts）換一張精簡配方：系統提示、這一輪的話、文風、全域要求、本章細綱、後 5 章邊界、本章已寫末尾、出場角色，外加近幾章定稿的連續性事實（`recentFacts`，≤3000 字）。前幾章細綱與前幾章全文第一次呼叫已經用過，每一輪都付一次全價不值；但一條前情都不帶也不行——百章實驗裡首輪常只寫到一半，續寫寫了一章的大半，死了的人在續寫裡又活過來。細綱配方同樣帶 `recentFacts`（P1）：全文大綱排在它後面，預算緊時先被擠掉，細綱就會排出與正文矛盾的事。收尾過早被回退的那一輪（`step.rewound`，五期補遺 §1.1）契約開頭多兩句：「收尾那一段已經拿掉了，寫足之後按本章細綱約定的結束狀態重新收尾」。

**執行卡後面跟一塊【本章邊界】**（五期補遺 §1.2、§1.3；禁用詞是百章實驗覆盤加的：生成層 `planWriting` 算好經 `BuildRequest.banned` 交過來，第一次呼叫點名不許用的詞，續寫那幾輪換成「已寫部分用了哪幾個、幾次」）：後 5 章細綱裡才排到、本章與前面各章都沒排過的人逐個點名「本章不出場：沈秋（第 4 章才登場）」（生成層 `planWriting` 按磁碟算好經 `BuildRequest.notYet` 交過來：帶角色卡上的稱呼、本章細綱自己提到的人不算，與寫完查的那一份同源；沒給時 `promptFactsOf` 從 focus 現算一份）；再重列比喻詞上限，續寫那幾輪換成「已寫部分用了 k 次，續寫部分最多再用 n 次」（`step.similes`）。三期首跑時邊界只有一句原則，第 3 章的結尾照樣把第 4 章的人寫了出來。

**系統提示加一條「用詞貼合年代」**（§1.5）：架構、大綱、細綱的「通用要求」第 4 條與正文的硬性要求第 7 條，古代、民國、架空世界不用 PTSD、抑鬱症、多巴胺、CPU 這類現代術語。越早的階段寫進去，後面每一層都照著抄。

三期加的四層：

| 層 | 注入什麼 |
|---|---|
| `guidance` | 小說配置的「全域要求」一節，單獨成段（`# 全域要求（每一章都要遵守）`） |
| `premiseWorld` | 小說配置（**除全域要求**，不重複帶）、故事前提、世界觀，一件一條 |
| `plotAhead` | 後 5 章的細綱一章一行（標題 + 關鍵事件前 300 字），標「絕對不要在本章提前寫出」。**按章號視窗取**（N+1..N+5，上游 GD:464-466），只帶排過的 |
| `chapterSoFar` | 本章已寫正文的最後 1600 字：「接著寫」讀磁碟，續寫那幾輪由生成鏈給（含這一次剛寫、還沒落盤的） |

「接著寫」時不帶上一章結尾：這一章的開頭早就從那裡接過了，兩個「從這裡接下去」擺在一起，模型會跳回上一章去。

**`revision`（上一版正文 + 修改意見）帶整章**（五期修）：從前是 `takeTail(…, 3000)`——3000 token 的尾巴，長一點的章前半截直接沒了，「重寫」時模型只能憑空重寫開頭，明細上還看不出少了什麼（第 2 條）。

四期加的一層（D18）：

| 層 | 注入什麼 |
|---|---|
| `evidence` | 前面各章的**定稿原文片段**：拿定稿過的細綱裡連續性事實的證據原句回到那一章的正文裡逐字定位，帶所在段落與前後各一段（移植 `chapter-materials.ts` 的 `assembleChapterMaterials`）。只認定稿之後正文沒再改過的章（細綱的 `sourceHash` 對得上正文）。前 5 章的事實全取，更早的只取提到本章角色（細綱 `characters[]` 與別名）的，最多 12 章、一共 6000 字，由近及遠填、按章號正序拼成一節「# 定稿原文片段（前情以這些原文為準……）」。正文層 P2 的第一層，續寫配方不帶 |

- **定位不到**（作者手改過細綱裡的事實或證據句）的那幾條換成事實原句，條目標 degraded 並寫明幾條；放不下的章 dropped 寫明是封頂了（第 2 條）。
- **與近章全文去重**：某一章整章正文進來了（`manuscriptFull`），它的片段改成 dropped、預算退回去——與上一章結尾片段同一個做法（`scratch.evidence`）。
- **D23**：上一章有正文卻還沒定稿，明細裡多一條 dropped 的「第 N 章 · 定稿原文」，寫明「沒有連續性事實，角色狀態截至第 K 章」；上一章定稿之後正文又改過，寫明「連續性事實不作數」；更早的章遇到這兩種靜默跳過。`characters` 層每張卡的說明帶「狀態截至第 K 章」。不擋路，但不靜默。
- **近章全文 0 章就是一章全文都不帶**（四期順手修掉：從前 `slice(-0)` 把前面每一章都整章塞了進來；現在各層取「最後 n 個」一律走 `takeLast`）。
- 上下文詳細度「精簡」整層不帶，出一條 `evidence:off` 的 dropped 說明。

幾處刻意的抬高（表裡加粗的幾條）：

- **正文階段文風指南升到 P0 force**。它是「讀者感覺不到換人執筆」的唯一保障，不該跟一段長對話搶預算——改之前它在 P1，一段長對話（封頂 30%）加幾張角色卡就能把它擠掉。
- **正文階段本章細綱也升到 P0 force**。細綱**就是**寫正文的依據：少了它，模型手上只有文風與前文尾巴，會自己編一章出來。
- **正文階段後 5 章細綱也是 P0 force**。那是邊界：沒有它，模型寫到章末時最順手的就是把下一章的事提前演掉，下一章於是無事可寫。
- **架構與大綱兩層的架構三件是 P0 force**。四件一件吃一件：前提照著配置寫、世界觀照著前提與角色寫，少了上一件，這一件就是憑空編的。
- **`settle`（落定細綱、落定設定）時歷史 cap 從 30% 抬到 60%、優先順序提到 P0**（`recipeFor(stage, capability)` 唯一一處按能力改配方的地方，不分階段）。這條命令要沉澱的就是那段討論，按常規由遠及近截掉等於把結論截沒了。**落定設定**（完善設定二期，架構那一層設定目錄上的 `settle`）另把 `lore` 層從 P2 的末尾提到歷史後面（P1），不讓角色卡先拿走預算；`lore` 層在這個目標上照設定清單那樣當規劃看（分類表 + 已有條目一行一條），關鍵詞命中的來源再加上歷史那幾輪（近的在前，明細裡寫「討論裡提到「X」」），命中的整條帶（含暗設，標明讀者還不知道）——要合併就得看得見原文；整條的名額放寬到一次落定的上限 12 條（`LORE_SETTLE_LIMITS`），字數另加 12 條的上限，不受詳細度那一檔的整條名額限制，預算放不下照樣降級、寫進明細。系統提示的原則與任務換成 [loreSettlePrompt.ts](loreSettlePrompt.ts) 那一份（`isLoreSettle`），合同按能力認、排在設定清單（`doc === 'lore'`）之前。

**細綱階段帶前後文而不是隻帶上一章**：前 3 章的細綱（梗概 + 關鍵事件 + 狀態變更）讓這一章接得上——發生了什麼、人物落在什麼處境；後 1 章（梗概 + 關鍵事件）讓它不至於把下一章要用的東西提前用掉。更早的章由前序細綱一覽一章一行帶，不再另帶一份：細綱與定稿是同一份檔案，同一份不帶兩遍。

**挑角色卡**：`selectCharacters` 第一優先是本章細綱的 `characters[]`（沒定稿時是計劃出場，D13——只在這裡用，不進出場統計），其後是這一輪輸入裡提到的、前兩章定稿過的細綱裡出場的與主角。

**前三個階段都不帶正文原文**：定架構、排大綱、拆細綱時讀三章正文既沒用又昂貴，一章三千字 × 近三章，夠裝下全文大綱還有富餘。

## 預算與降級

| 優先順序 | 預算不足時 |
|---|---|
| P0 · force | 永遠保留（系統提示、使用者這一句、本層產物） |
| 使用者 @ 的引用 | 單條封頂預算 35%，超出從頭部截斷而非丟棄 |
| 會話歷史 | 整體封頂按上下文詳細度（預設 30%，`settle` 時固定 60%）、單輪 12%，由近及遠保留，更早的整輪丟棄。**已經寫入的那一輪（`acceptedTo`）與發起它的命令輪不帶**（五期補遺 §1.4）：它們落了盤，有專門的層按磁碟帶，落盤後手改過的話歷史裡還是舊版；明細裡記「已寫入 xxx，以磁碟上那一份為準」。討論與沒採納的那一版照舊帶。**已經移除的內建 agent 跑的那幾輪（`isBuiltinAgentTurn`）與交給它的那句指令也不帶**：那是排程過程，不是討論 |
| 角色卡 | 降級為要點：「身份 + 當前狀態 + 暗設」三節（寫正文時暗設本來就不帶，只剩前兩節） |
| 某章正文 | 降級為該章細綱（沒定稿的標「計劃，沒定稿」）→ 丟棄 |
| 規劃時一章一行的前情（大綱的中段、前序細綱一覽） | 大綱最多 `outlineBriefMax` 章（預設 100）、一覽最多 `plotListMax` 章（預設 30），由近及遠放到預算用完，截過的標 degraded 並寫明哪幾章沒帶；更早的交給全文大綱（P1），明細裡寫它寫到第幾章 |

預算 = `contextWindow - maxOutputTokens - 512`，並與 provider 的 `maxInputTokens` 取小。

- **第 3 級就是從前的行為**，只多幾條：設定封頂（從前命中就整條塞、不排序不封頂，幾百條的書會把視窗填滿）；拆細綱帶敘事線（從前一條都不帶）；續寫大綱時只帶第一行的那一段封頂 100 章（2026-10-22，從前一章不落地全列、強制帶，128k 視窗七八百章撐爆）；前序細綱一覽 100 章降到 30 章、規劃時角色圖譜只給近 20 章出場的一段（2026-10-24，第 83 章單章細綱、46 張卡的假工程從約 4.9 萬降到約 2.2 萬估算 token，[設計稿](../../../docs/design/plans/2026-10-24-planning-roster-plotlist.md)）。規劃時的設定一覽按遠近排、拆細綱的伏筆重排與名額外只列名字、設定關鍵詞最長匹配（2026-10-25，寫到後面老設定、老伏筆不再霸佔名額，[設計稿](../../../docs/design/plans/2026-10-25-context-aging.md)）。
- **更早幾十章的細綱不再帶**（2026-10-21，原 `plotSummary` 層與 `summaryChapters` 一項，那一項從前封頂 60 章）：寫正文、寫大綱各帶一大片概要，上下文越寫越胖，正文還被概要腔帶著走。寫正文只帶前幾章細綱，更早的前情由全文大綱接著。
- **因級別少帶的都留說明**（第 2 條）：`evidence:off`、角色卡「只帶身份/當前狀態/暗設」（寫正文時「只帶身份/當前狀態」）、前序細綱一覽「只帶最近 N 章」、大綱「第 a–b 章沒逐章列」、角色圖譜「其餘 N 人只列名字」都寫出是哪一級。原有的上限說明（「敘事線一次只帶 6 條」「定稿原文片段一共只帶 6000 字」）措辭不變，數字跟著級別走。
- **不分級的**：後 5 章邊界（`AHEAD_PLOTS`——生成層算「本章不出場」用同一個視窗，兩邊必須一致）、本章已寫末尾 1600 字、@ 引用 35%、`settle` 的歷史 60%、整份帶的文件層；定稿、全文大綱、角色狀態、建卡、記設定、建條目與整合（輸入就是那一章本身或按視窗分批，調低只會截掉要整理的東西、或多拆幾次呼叫）。
- **任何一級都不改呼叫次數**（第 4 條），只改每次帶多少。
- 裝配結果帶 `detail`：裝配清單的摘要行寫「詳細度：詳細」，「上下文已裝配」那條日誌也寫；批次寫章的確認框寫當前級別。
- 設定頁原來的「注入完整原文章數」「上一章結尾字數」兩個輸入框並進了級別。config.json 裡的舊鍵不再讀（設定頁儲存過一次的人這兩個數都在檔案裡，分不清是不是手改的），下一次儲存時清掉。
- 測試要單獨改某一項（例如「近章全文 0 章、其餘照預設」）用 `NovelConfig.contextOverrides`；走 `readConfig()` 的鏈路用 `config.ts` 的 `setContextLimitsOverride`。兩樣都不從 config.json 讀：作者能動的只有級別。

## 關鍵設計

- **不靜默截斷**：每條 `ContextItem` 帶 `status`（included / degraded / dropped / excluded）與人類可讀的 `note`，前端摺疊展示。作者隨時知道這次沒帶上什麼。
- **發出去的那份原樣留著**：對話頁那一輪的 `built.messages` 記在回覆上（`ChatTurn.contextMessages`，隨會話落盤，只記第一次呼叫——續寫、修復那幾輪另行裝配），裝配清單摘要行上「複製完整上下文」一下複製整份。日誌照舊只記條目名與 token 數（第 11 條）；工程頁批次與 MCP 的 `generate` 不留。
- **層與配方分離**：「帶什麼」在 recipes、「怎麼取」在 layers。讓細綱階段不帶正文原文是配方里少寫一行，不是裝配器裡多一個 if。
- **只讀用得上的檔案**：`resolveFocus` 按配方決定讀不讀前後章的細綱。正文階段每次生成都多讀三章用不上的細綱，那是落在關鍵路徑上的浪費。
- **引用在 P0**：使用者特意 @ 的內容不該被自動裝配擠掉。
- **歷史是多輪訊息**：會話歷史按 role 交替作為真正訊息發出，不是塞一段「以下是之前的對話」；單輪過長取結尾（越靠後越接近當前進度）。
- **去重**：上一章正文能完整放下時，P0 的結尾片段自動撤掉，同一段文字不在 prompt 裡出現兩次。沒有正文的章（只排了細綱）`manuscriptFull` 跳過，它在前幾章之內時細綱由 `plotPrev` 帶。
- **正文只讀 `chapters/`**：一章一綱之後正文只在一處，從前還要回落到中轉站 `manuscripts/`。只有 `chapters/` 的老工程一樣帶得出前文。
- **討論型能力禁止改寫產物**：`outputKindOf(action) === 'text'` 時系統提示裡明寫「只回答，不要輸出改寫後的完整產物」。少了這一條，模型會一邊回答一邊把整份劇情細綱重寫一遍，而介面上那一版是不能採納的。
- **細綱可以寫具體場面，但不是正文**：從前細綱被禁止寫畫面與動作、只許寫抽象的因果鏈，模型拿它去「擴寫」出來的是流水賬。現在細綱就是定稿那七節（連續性事實計劃時空著，定稿時才生成；敘事線二期刪了「新增伏筆」）：「關鍵事件」一條一件事、按發生順序（3–6 條、合計 100–300 字，與定稿寫出來的列表同一個樣子，定稿才能逐條改而不是重寫），可以寫到具體場面，梗概與關鍵事件必填、出場人物至少一人；「看點」寫爽點，也寫章末吊著讀者的那一下，過渡章沒有爽點就只寫鉤子，時間地點、看點、狀態變更都可以空著；合同裡另有 `threads`（這一章在敘事線上的計劃：推進 / 關係 / 收束 / 埋〈伏筆〉/ 收〈伏筆〉，一章最多 6 條，不進細綱，寫入時寫進各條線），以及一條【敘事線】規矩——照著「敘事線」那一節排，標著「本批要收」「已過第 N 章，還沒收」的伏筆必須在這幾章收，收不了寫明推遲到第幾章（原來「伏筆強制回收與釋放」那一句並進來了）；不寫成段的描寫與對白。單章與批次用同一份藍圖合同（`{"blueprints":[…]}`，單章就是隻有一項），外加上游的章節容量合同（目標字數 ±20%）。
- **`settle` 與 `generate` 的差別只在系統提示**（`CAPABILITY_TASK`），**輸出契約必須一字不差**：同一份細綱不該因為入口不同長得不一樣。
- **暗設不進正文，揭開靠細綱**（完善設定，2026-10-19）：寫正文時看不見暗設，揭開那一章的正文模型只能從細綱知道。細綱合同（寫細綱、落定細綱、批次拆細綱同一份）多一塊【暗設】：標著「暗設（讀者還不知道）」的，這一章不打算揭開就別寫進梗概、關鍵事件、看點與「設定」一節的 note，要鋪墊寫成 `threads` 裡的一條「埋」（敘事線二期；原來寫進新增伏筆）、只寫讀者看得到的那一面；打算揭開就在關鍵事件裡單列「揭開：……」。大綱合同同一個口徑（第 10 條要求）——大綱拆成細綱，細綱進寫正文的上下文。

## 依賴關係

依賴 `model/`（讀架構、大綱、細綱、正文、全文大綱、角色卡、設定；`model/pipeline.ts` 提供 Stage × Capability × Target，`model/structureGuide.ts` 算結構區間，合同的字數上限也在 model 裡）與 `llm/`（`ChatMessage` 型別）。**不依賴 `features/`**。被 `generation/`（對話頁單次生成與生成鏈）與 `features/pipelineBatch.ts`（工程頁批次）呼叫——兩者走同一個 `buildContext`，因此批次與單次產出的是同一個質量。
