一句話方案：**單條設定可以當生成目標（展開），討論結論可以落定成一批條目（落定設定），名錄指出接下來幾章要用、卻還是空的設定（待完善）；條目多一節「暗設」，規劃時看得見、寫正文時看不見。**

## 現狀：設定只會往回長

1. **條目的正文要等正文寫出來才有**。正文只有三個來源：

   | 來源 | 什麼時候 | 能寫多細 |
   |---|---|---|
   | 架構 · 設定清單 | 開書時一次排 12–30 條 | 初稿合計 ≤300 字，沒寫到的節寫「（未交代）」（`loreFile.ts:56`、`loreList.ts:272-303`） |

   | 整合 | 條目水位之後又定稿了幾章 | 只並定稿正文新確立的事實 |

   唯一一份寫單條的提示詞 `LORE_ENTRY_SYSTEM` 第 1 條就是「只寫給出的記錄裡明確有的，不補完、不推測」（`features/lorePrompt.ts:48`）——那是往回記的規矩，往前想不能借它。
2. **細綱帶出的新設定只是空條目**：`createPlannedLore`（`generation/accept.ts:584-607`）只寫標題和一句話（note ≤60 字），正文留空，註釋原話「等寫到了、定稿過，再從名錄裡整合」。而且**只有批次拆細綱會建**：單章「寫細綱 / 落定細綱」的 `acceptPlot`（`accept.ts:417-463`）只把第九節寫進細綱，`plannedLore` 也只認批次（`accept.ts:86-98`）——和上一期設計稿「新設定隨細綱一起建空條目」「批次拆細綱與 `/落定细纲` 用同一份合同」的本意不符。
3. **討論結論落不進條目**：生成目標只有設定文件 / 大綱 / 細綱 / 正文四種（`model/pipeline.ts:371-375`）；落定只在細綱階段有（`pipeline.ts:178-183`）；`generate` 只認整個設定目錄，也就是整批設定清單（`tools/novel/generate.ts:323-329`）；閘道器的種類表對一條設定不給階段與目標（`workspace/kind.ts:216-219`）。聊定了只能手抄。

## 資料格式

### 條目多一節「暗設」

```markdown
## 概要
## 規則與邊界
## 現狀
## 暗設
```

- 可選的第四節：讀者還不知道的真相——真實身份、來歷、規則背後的真正原因。**≤200 字，不算進明面的 600**（`LORE_ENTRY_LIMITS` 加 `暗設: 200`，`body: 600` 仍指前三節）。
- **認法**：以「暗設」開頭的二級標題（`## 暗設`、`## 暗設（未揭示）` 都認），到下一個二級標題或文末為止。純函式 `splitLoreHidden(body) → { visible, hidden }` 放 `model/loreFile.ts`。作者寫成別的標題就當明面（第 1 條：認不出就照常讀）。
- **誰看得見**：

  | 場合 | 帶不帶暗設 |
  |---|---|
  | 設定 / 大綱 / 細綱階段（討論、生成、落定） | 帶，標明「暗設（讀者還不知道）」 |
  | 正文階段（寫、接著寫、重寫、討論正文）與續寫 | **不帶**，明細裡注一句（第 2 條） |
  | 正文階段 @ 引用一條設定 | **不帶**，明細裡注一句；要讓正文知道，就寫進這一章細綱 |
  | 審稿、修稿 | 這兩張配方本來就不帶設定（`recipes.ts:217-267`） |
  | 展開、整合、落定設定 | 帶（要改的就是它） |
  | 一行（`brief`） | 提示詞不許把暗設寫進一句話；缺 `brief` 時取正文第一句（`loreBrief`，`loreFile.ts:161-175`）跳過暗設那一節 |
  | 定稿 / 記設定的 `loreHint` | 只給標題、分類、關鍵詞（`loreRecord.ts:59-67`），不碰正文；提示詞不許把暗設裡的東西寫進關鍵詞 |
  | MCP `read` | 原文——外部 agent 是排程者，不是寫正文的那個模型（第 24 條） |

- **揭開靠細綱**：細綱階段的提示詞加一條——暗設是讀者還不知道的事，這一章不打算揭開，就別寫進梗概、關鍵事件、看點；要鋪墊就寫進「新增伏筆」，只寫讀者看得到的那一面；打算揭開，就在關鍵事件裡寫明「揭開：……」。細綱進正文的上下文，揭開那一章的正文模型從細綱知道這件事。
- **整合**：`LORE_ENTRY_SYSTEM` 加一條——記錄表明正文已經揭開了暗設裡的某件事，就把它挪進前三節、從暗設裡刪掉；沒揭開的原樣保留（那是作者的計劃，正文沒推翻）。
- 全書查詢替換保護的標題（`model/bookFind.ts:66`）加「暗設」。
- **為什麼不學敘事線「帶上，註明別揭開」**：敘事線一條一句、有明確的揭開章號；條目的暗設沒有章號，和明面混在同一條裡整條帶，正文模型看見就容易說漏。寫正文字來也不需要知道真相——需要的鋪墊，細綱裡已經寫了。

### 薄條目怎麼認

`loreThin(entry)`（`model/loreFile.ts`，純函式），下列任一就算「還只有一句話」：

- 明面正文（去掉暗設）是空的；
- 是「新建設定」留下的佔位（以「（在這裡寫這條設定」開頭，`features/characters.ts:345`）；
- 三節都只寫著「（未交代）」。

不按字數猜——作者寫了兩行就是作者認為夠了。`hasContent`（`model/markdown.ts:304-307`）只認「（待補充）」，不動它。

## 1. 展開一條設定（一期，1 次）

### 生成目標

- 新增目標 **`{ kind: 'lore'; relPath }`**，階段是 `setting`。照細綱 `plotRelPath` 的路子：目標自己帶著檔案身份。
- **不復用** `{ kind: 'setting', doc: 'lore' }` 加一個路徑：凡是 `doc === 'lore'` 的分支都會走設定清單那條鏈（`structured.ts:599-614`、`prompts.ts:690-692`、`artifact.ts:137`），`targetKey` 會把單條和整批當成同一個目標，`normalizeTarget` 會丟掉多出的欄位——隨會話存下的草稿重開後會被當成整批清單採納（`model/session.ts:620`）。
- `kindOfPath` 的設定分支給出 `stage: 'setting'`、`target: { kind: 'lore', relPath }`（`kind.ts:216-219`），MCP 的 `generate` 不用特判就認條目路徑。
- 要改的地方：窮舉 switch 編譯器會抓（`targetKey`、`describeTarget`、`pathOfTarget`、`targetHasContent`、`normalizeTarget`）；**要人工逐處查的是「不是 setting 就當 config」的那些**（`artifact.ts:133`、`prompts.ts:176` / `:683`、`background.ts:131-134`、`focus.ts:98`、`builder.ts:309`、`views/workbench.ts:59`、`views/stateBrief.ts:84`、`media/src/view/pipeline.ts:131`、`media/src/view/project/nextSteps.ts:106`；動手前 grep `kind === 'setting'` 全部過一遍）。
- 這個目標上的能力：討論（聊這一條）與生成（展開，介面叫「展開這條設定」）。

### 喂什麼

| 優先 | 內容 |
|---|---|
| P0 | 配置、前提、世界觀；這一條現有的全部內容（含暗設）；作者這次的話（可以空） |
| P1 | **已排細綱裡用到它的地方**：沒定稿的細綱第九節點名它的那一行，以及梗概、關鍵事件裡提到它（標題或關鍵詞）的句子，帶章號——展開是為這些情節服務的 |
| P1 | **定稿過的記錄**：與建條目、整合同一份（`recordsAbout`，`features/lore.ts:95-123`）——已經寫進正文的，不能推翻 |
| P2 | 相關條目：同目錄的、關鍵詞在本條或上面那些句子裡命中的，整條 / 一行照 lore 層的規矩封頂；角色一行一人 |

細綱與定稿記錄合計照整合的 `MATERIAL_TOKENS` 封頂，放不下的進明細（第 2 條）。

### 合同（新寫一份，不借 `LORE_ENTRY_SYSTEM`）

```json
{
  "brief": "…",
  "keywords": ["…"],
  "body": { "概要": "…", "規則與邊界": "…", "現狀": "…", "暗設": "…" },
  "children": [{ "name": "…", "category": "…", "brief": "…" }],
  "questions": ["…"]
}
```

1. **為已排的情節服務**：細綱裡打算讓它做什麼，它就得撐得住；和劇情無關的百科不寫。
2. **定稿記錄裡已經確立的不許改**；作者現有的內容是作者認過的，沒理由不刪，只補、只細化。
3. 字數上限同第 27 條；暗設 ≤200 字，沒有就給空。
4. 關鍵詞 3–8 個，只放讀者會看到的叫法；人名不算；暗設裡的東西不進關鍵詞、不進一句話。
5. `children`：寫不下、值得單獨一條的部分，≤3 條，只給名字、分類、一句話。
6. `questions`：2–5 條還沒定、要作者拍板的問題（「閣規是成文的還是口傳的？」），不問已經定了的。

程式校驗（不加呼叫）：一句話截 40 字；四節按上限截（同 `normalizeLoreBody` 的做法）；新關鍵詞過 `cleanLoreKeywords`；`children` 里名字已有條目的、是人名的、重名的丟掉；`questions` 最多 5 條、每條 ≤60 字。**解析不了就報失敗、不給寫入**，不做全文兜底——條目被一段沒解析開的原文蓋掉，比沒寫更糟（同定稿）。

### 落盤

- 新增產物 **`loreEntries`**（展開與落定設定共用）：`{ entries: LoreDraft[], questions: string[] }`。展開時 `entries[0]` 是目標條目，**按 `relPath` 認、不按標題**（展開不改名），其餘是 `children`（正文空）。
- 目標條目：
  - 明面正文是空的、是佔位 → 直接寫；其餘走覆蓋審閱 diff（第 3 條）。
  - 關鍵詞只增不減；一句話新的優先；正文整份換成展開後的。
  - `bodyHash` = 新正文的指紋，記作機器寫的（定案 4）。
  - 水位與整合同一個演算法（`integrationWatermark`，`lore.ts:67-81`）：展開喂的定稿記錄就是整合會喂的那一份，寫完 `＋N` 也就收了。
- `children`：隨卡片一起建空條目（與細綱帶出新設定同一個第 19 條例外），卡片上列「會新建設定條目：……」（`plannedLore` 擴到 `loreEntries`）。
