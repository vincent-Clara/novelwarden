# 分卷層與「劇情段」的正名

**狀態**：已實現。

在 `outline.md` 與 `plots/` 之間插一層**卷**，並把「一份細綱 = 一章」這條隱含的
等式拆開：規劃的單位是**劇情段**，管理的單位是**章**，兩者是兩條獨立的軸。

---

## 為什麼

### 1. 大綱直接拆章，跨度太大

從前 `outline` 階段的 `split` 一次吐出一批章骨架。實際跑起來是這樣的：

```
使用者：大綱：赤星臨近，全球變異…女主覺醒「掌握」能力…
模型：（寫好 outline.md，隨即）拆出 5 章的細綱，每章一句目標
```

全書大綱那一兩千字裡**沒有足夠的資訊**去決定第 7 章該發生什麼。模型只能一次
給出五章骨架，而那五章彼此的因果薄得像一份目錄——它們不是「劇情」，是標題。
緊接著的「批次寫劇情」會照著這份目錄往下拆，錯誤就這樣一層層放大。

中間缺的是一個**中等尺度**：一條完整的弧線，有自己的開局、升級與收束，十幾到
幾十萬字。有了它，「接下來該發生什麼」才答得準。

### 2. 「章」這個詞在兩處騙人

設計上早就承認了「生成時不按章硬切」：模型按劇情的自然長度寫，正文落在中轉站，
作者標斷點，一份正文可以拆成兩章、三章。但介面上那個單位仍然叫「第 N 章」，
於是：

- 作者以為「第 4 章」將來就是書裡的第 4 章——**它可能變成第 4、5、6 章**。
- 一段拆成三章之後，為了維持「細綱與章同號」，後面**每一份**還沒拆的細綱都要
  整體改名讓路，連帶搬走各自的場景目錄與中轉站正文。一次幾十份檔案的重新命名
  風暴，只為維持一個作者根本不需要的等式。

---

## 改成什麼

```
outline.md ──拆卷──▶ volumes/NN-卷名.md ──拆段──▶ plots/NN-卷名/NNN-段名.md
           ──拆場景──▶ scenes/… ──▶ manuscripts/… ──拆章──▶ chapters/…
```

### 卷不是一個創作階段

`CreationStage` 仍然是四個（大綱 / 劇情 / 細節 / 正文）。卷只做兩件事：

- **收納**：劇情段按卷落進 `plots/<卷词干>/`。
- **拆分**：從卷綱拆出下一個劇情段。

所以 `CreationTarget` 多一個 `volume`，而 `stageOfTarget` 把它歸到 `outline`
——分卷與拆段都是「策劃編輯」這個身份的活，用的也正是大綱那一套上下文
（全書大綱 + 全書摘要）。少一個階段就少一套配方、一套提示詞、一組能力按鈕。

代價是**同一個 `stage × capability` 在兩種 target 上做的事不同**，所以這三處都要
收 target：

| 位置 | 全書大綱 | 某一卷 |
|---|---|---|
| `labelOf` / `commandsFor` | 「拆成卷」 | 「拆出劇情段」 |
| `buildOutputContract` | 分卷清單 JSON | **一個**劇情段 JSON |
| `parseArtifact` | `volumeList` | `plotSegment` |
| `acceptArtifact`（`outlineDoc`） | 寫 `outline.md` | 寫那一卷的卷綱 |

### 一次只拆一段

`plotSegment` 刻意不是列表。理由與「大綱直接拆章」是同一條：一次吐五段只會得到
一串彼此沒有因果的骨架。一次一段時，模型手上有卷綱（`volumeSelf`）也有這一卷
已經排到哪了（`volumeSegments`），兩層都是 P0 force——少了後者它會把已經排過的
那幾段重新發明一遍。

模型不聽話給了三段時**只取第一段**：契約是一次一段，收下三段會讓這條設計在資料
這一側悄悄失效，而作者以為自己點的是「拆一段」。

### 段號與章號是兩條軸

- **段號**（`plots/` 裡的檔名字首）只是**排序鍵**。`nextPlotNo()` 仍跨
  `plots/` 與 `chapters/` 取最大號 +1，好讓新建的段在檔名上排在最後。
- **章號**自己連續排（`nextChapterNo()` = 最大章號 + 1）。讀者按章追，章號必須連續。
- 介面上劇情段稱「**劇情 N**」，那個 N 是 `segmentDisplayNo(最新章號, 位次)`
  ——最新章號 + 在未交付的段裡排第幾。

舉例。拆出 5 段、一章都還沒有：顯示劇情 1~5。把第 1 段寫完、拆成了 3 章
（第 1~3 章）：那一段從待做列表裡消失，剩下 4 段接著往下數——劇情 4~7。
老工程寫了 99 章、現在開始規劃：第一段就是劇情 100。

於是**拆分不再改任何別的檔案**。那次重新命名風暴整個消失了。

### 「段 → 章」的鏈是顯式的

`chapters/` 下的檔案是作者的東西，拆分之後外掛一個位元組都不往裡改，所以這條鏈
只能記在段這一側：`splitManuscript` 把建好的章節路徑寫進細綱的 frontmatter
（`chapters:`）。

老工程沒有這個欄位。那時**只對 `plots/` 根下的段**退回同號判定
（`views/pipeline.ts` 的 `chaptersOfSegment`）：本層出現之前一段就是一章、兩者
同號，那些工程一個位元組都沒改就得能繼續用。

**兜底只對根下的段生效**是有意的：新口徑下段號會與章號撞車（一段拆成三章，
後面的段號不再讓路），拿同號去認會把一個剛拆出來的空段誤判成「已經交付」——
那一段會從待做列表裡憑空消失。根下不會有這種誤判，因為分卷之後新建的段都落進
卷目錄，`newPlotFlow` 也把手工新建的段放進最後一卷。

### 映象規則：從「檔名詞幹」推廣到「plots/ 之下的整段路徑」

```
plots/01-觉醒之日/007-入宗.md
  → scenes/01-覺醒之日/007-入宗/
  → manuscripts/01-觉醒之日/007-入宗.md
```

未分卷的段（根下那些）映象出來自然就是扁的，與本層出現之前**完全一致**——所以
老工程一個檔案都不用搬。這與「摘要映象 `chapters/` 下的相對路徑、分卷子目錄照樣
帶上」是同一條規則，只是軸換成了 `plots/`。

`kind.ts` 的反推因此按**最後一個** `/` 切（前面全是映象鍵，後面是檔名），仍然
零 I/O。

代價：**卷改名要搬三棵目錄樹**（`plots/` `scenes/` `manuscripts/` 各一棵，卷詞幹
是三處的第一級目錄名）。只搬 `plots/` 那一棵的話，一卷改名之後每一段都會顯示
「還沒拆場景」，而那些場景就躺在旁邊一個孤兒目錄裡。見
`workspace/handlers/volume.ts` 的 `carryVolumeCompanions`。

### 指紋鏈多一環，粒度反而變細

```
outline.md ───hash──▶ volumes/*.md      (upstreamHash)
volumes/V.md ─hash──▶ plots/V/*.md      (upstreamHash)
plots/X.md ───hash──▶ scenes/X/*.md     (upstreamHash)
```

從前細綱的上游是全書大綱，於是**改一句立意換來一屏 ⟳**。現在劇情段的上游是
它所屬那一卷，改一卷的走向只讓那一卷的段標髒。未分卷的段退回全書大綱——它們
本來就是那樣記的。

### 介面

工程頁多一組「**卷**」，排在章節之前（它是章節的上游，也是拆劇情段唯一的入口）。
**前端複用章節行的元件**，所以 `ProjectVolumeNode` 與 `ProjectPlotNode` 刻意同形
——同一套骨架讀兩種資料時，欄位對不上就得在前端寫分支。

「章節」那一組變成一條**時間線**：已釋出的章在前，還沒交付的劇情段在後，中間
一條虛線分界，那就是「我寫到哪了」。兩種行的說法完全不同（「第 12 章《夜訪》」/
「劇情 4《樓道》」），所以 `label` 由後端給——前端按 `no` 自己拼會把每個劇情段
都叫成「第 N 章」。`PlotSummaryView` 同理多一個 `label` 與 `emptyHint`。

分成兩組會讓作者在兩邊之間來回找同一件事（「我寫到哪了」），所以合成一列。

## 不改的東西

- **四層裝配與提示詞的質量來源一個字沒動**：`recipes.ts` 裡卷借大綱那一張配方，
  三個與卷相關的層在 target 不是某一卷時自然是空的。複製一份出來，下次改大綱層
  的裝配策略就會漏掉一邊（與 `settle` 只微調既有配方同一條理由）。
- **落盤前必須過一遍人**（第 19 條）：新增的兩條路徑（拆卷、拆段）走的是同一張
  落盤卡片。
- **老工程不需要遷移**：`volumes/` 是空的、`plots/` 是扁的、段與章同號——三條
  一起構成「純老口徑」，而每一條都單獨有兜底。
